# Как внести вклад в проект

Спасибо за интерес к VoiceMeeter IdleWatcher. Приветствуются сообщения об ошибках, небольшие улучшения и исправления документации.

Это небольшая Windows-утилита с намеренно консервативной логикой выключения и управления жизненным циклом API. Перед предложением изменений реализации ознакомьтесь с этими правилами.

## Перед созданием Pull Request

- **Сообщение об ошибке:** создайте Issue через форму Bug report. Укажите точный тег релиза или SHA коммита и короткие шаги воспроизведения.
- **Отчёт о тестировании:** используйте форму Test report. Укажите точную ревизию исходников, среду, область проверки, результат и необходимые отредактированные диагностические данные. Проверяйте только исходный код репозитория или сборку, явно разрешённую сопровождающим; не запускайте исторические Portable ZIP, распространение которых приостановлено.
- **Предложение функции:** используйте форму Feature request или начните обсуждение в [GitHub Discussions](https://github.com/AnAllegory/VoiceMeeter-IdleWatcher/discussions). Существенные изменения поведения или архитектуры следует сначала обсудить.
- **Уязвимости безопасности:** не публикуйте сведения о неисправленной уязвимости в открытом Issue или Discussion. Следуйте инструкциям в [SECURITY.md](SECURITY.md).
- **Вопросы:** используйте [GitHub Discussions](https://github.com/AnAllegory/VoiceMeeter-IdleWatcher/discussions).

Перед созданием новой темы проверьте, не обсуждалась ли она уже в Issues или Discussions.

## Среда разработки

Поддерживаемая среда запуска:

- Windows.
- Windows PowerShell 5.1 (редакция Desktop). Не добавляйте синтаксис и зависимости, доступные только в PowerShell 7.
- VoiceMeeter с Remote API для ручных runtime-проверок.

Все семь рабочих файлов должны оставаться вместе в папке приложения. Сохраняйте порядок импорта модулей:

Support -> Interop -> MacroButtons

Для отступов в исходниках PowerShell, VBS и C# используйте табуляцию, а не пробелы. Сохраняйте контракт маркера пути к DLL в C#: __VOICEMEETER_DLL_PATH__ должен встречаться ровно один раз внутри verbatim-строки и заменяться модулем Interop после чтения исходника в UTF-8 с корректным экранированием кавычек пути.

## Контракты безопасности и архитектуры

Изменения реализации должны сохранять текущую модель безопасности, если отдельное изменение архитектуры заранее не обсуждено и явно не одобрено:

1. Автоматическое выключение VoiceMeeter требует достижения заданного порога бездействия и полностью выключенного дисплея Off (0). Состояния On, Dimmed, неизвестное или недоступное должны блокировать выключение.
2. Непосредственно перед Command.Shutdown повторно проверяйте бездействие, состояние дисплея и отсутствие запроса штатной остановки /stop. Не ослабляйте и не обходите финальную проверку.
3. MacroButtons остаётся необязательной функцией, ошибки которой не должны блокировать основную работу. Сохраняйте единственный writer Invoke-MacroButtonStateSync.
4. Режим STATEONLY (0x00000002) должен оставаться фиксированным внутри модуля MacroButtons. Не делайте его настраиваемым и не добавляйте считывание GetStatus или опрос MacroButton_IsDirty.
5. Записывайте состояние MacroButtons только при известном состоянии API и подтверждённо работающем движке VoiceMeeter. После IsParametersDirty = -2, подтверждающего остановку сервера, не пытайтесь выполнять новые записи; сохраняйте последнее состояние, принятое API.
6. Не добавляйте опрос процессов, WMI-подписки, обработчики Process.Exited или второй writer MacroButtons в качестве обходного пути после остановки API.
7. Успешный код возврата Remote API означает, что команда принята. Это не доказывает, что интерфейс MacroButtons визуально обновился.

Это осознанные контракты проекта, а не случайные детали реализации. Перед изменением связанного кода прочитайте [ARCHITECTURE.md](ARCHITECTURE.md), [PROJECT_CONTEXT.md](PROJECT_CONTEXT.md), [ROADMAP.md](ROADMAP.md) и [AGENTS.md](AGENTS.md).

## Тестирование и доказательства

Публичный workflow GitHub Actions проверяет разбор Windows PowerShell 5.1, проектные контракты, компиляцию C# interop с подстановочным путём DLL, обработку неверного аргумента VBS-запускателем и PSScriptAnalyzer. Успешный CI означает прохождение статических проверок. Он не запускает VoiceMeeter и не проверяет реальный Remote API или интерфейс MacroButtons.

Для изменений кода:

- По возможности выполните локальные проверки и точно укажите, что именно запускали.
- Дождитесь завершения workflow для Pull Request и исправьте блокирующие ошибки.
- Если выполняли ручной runtime-тест, укажите версии Windows и VoiceMeeter, точный тег проекта или SHA коммита, шаги и наблюдаемый результат.
- Разделяйте проверку исходников, результаты статического CI и наблюдения сопровождающего на реальном ПК. Не выдавайте одно за другое.

Не публикуйте в Issue и Pull Request пароли, API-токены, коды восстановления, закрытые ключи, неотредактированные журналы, личные данные и посторонние локальные пути.

## Pull Request

1. Если у вас нет права записи в репозиторий, создайте fork. Затем создайте отдельную ветку на основе актуальной публичной ветки main и направьте Pull Request в main.
2. Держите набор изменений небольшим и объясните, какую проблему он решает.
3. При наличии связанного Issue добавьте ссылку на него.
4. Опишите изменения поведения, влияние на совместимость и результаты проверок.
5. При изменении пользовательского поведения или инструкций обновите оба README.
6. Если изменения затрагивают архитектуру, план развития, историю изменений или документацию релиза, обновите соответствующие документы.
7. Не создавайте и не перемещайте публичные теги релизов, не публикуйте релизы и не меняйте номера версий в рамках обычной работы. Публикация релиза является отдельным действием под контролем сопровождающего.

Pull Request является предложением на рассмотрение, а не обещанием автоматического принятия изменений.
