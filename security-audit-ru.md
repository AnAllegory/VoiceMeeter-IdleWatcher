# Проверка исторических Portable ZIP

**Дата отчёта:** 26 ноября 2026 года  
**Статус:** предварительные технические результаты. Это не сертификат отсутствия вредоносного ПО и не разрешение на распространение архивов.

## 1. Цель и область проверки

Проверялись исторические Portable ZIP-файлы VoiceMeeter IdleWatcher версий 1.0.5 и 1.0.6 после двух сообщений:

- по сообщению сопровождающего проекта, Microsoft Defender обнаружил `Trojan:Script/Wacatac.H!ml` в Portable ZIP версии 1.0.6;
- Google Search Console ранее показывала проблему категории **Harmful downloads** для исторического URL загрузки версии 1.0.5.

Эти сообщения стали поводом для расследования. Настоящая проверка **не устанавливает**, почему каждый из продуктов классифицировал архив, и не доказывает, что срабатывание было ложным.

Оригинальные ZIP-объекты восстановлены из истории Git репозитория по их Git blob ID. При проверке не запускались скрипты, исполняемые файлы или другие файлы проекта.

## 3. Методика

Окончательная проверка выполнялась в GitHub Actions, запуск **45856043583** (номер запуска 12), на выделенном GitHub runner с **Windows Server 2025 Datacenter**.

Сценарий:

1. восстановил два ZIP-объекта из истории Git;
2. записал размер и SHA-256;
3. разобрал локальные заголовки ZIP и извлёк сохранённые байты файлов без их исполнения;
4. вычислил CRC32 каждой локальной записи и сравнил с контрольной суммой в её заголовке;
5. разобрал End of Central Directory (EOCD) и центральный каталог;
6. выполнил дополнительную диагностическую интерпретацию записей центрального каталога v1.0.6 с фиксированной частью 44 байта, чтобы проверить соответствие локальным заголовкам;
7. сравнил файлы реализации и конфигурации v1.0.6 с соответствующими файлами исходного дерева v1.0.6;
8. выполнил ограниченный статический поиск по заданным шаблонам и выборочное сканирование Microsoft Defender.

Ни один файл проекта не запускался. Сценарий проверки находится во [временной ветке security-review](https://github.com/AnAllegory/VoiceMeeter-IdleWatcher/blob/security-review/historical-zip-scan-2026-11-26/.github/workflows/historical-zip-security-review.yml). Окончательный запуск завершился успешно: [GitHub Actions, запуск 45856043583](https://github.com/AnAllegory/VoiceMeeter-IdleWatcher/actions/runs/45856043583).

## 4. Результаты проверки целостности архивов

### v1.0.5

- Найдено 9 локальных заголовков: 8 файлов и запись каталога верхнего уровня.
- Все 9 локальных записей прошли проверку CRC32.
- EOCD указывает на 9 записей.
- Стандартный разборщик центрального каталога прочитал 9 записей; их количество и метаданные согласуются с локальными записями.

**Вывод:** структура v1.0.5 согласуется с проверенной стандартной схемой центрального каталога ZIP. Это вывод о целостности контейнера, а не вердикт об отсутствии вредоносного ПО.

### v1.0.6

- Найдено 8 локальных заголовков файлов.
- Все 8 локальных записей прошли проверку CRC32.
- EOCD указывает на 8 записей и размер центрального каталога 833 байта.
- Разбор центрального каталога по стандартной схеме с фиксированным заголовком 46 байт не дал 8 корректных совпадающих записей. Стандартный разборщик распознал только одну некорректную/несовпадающую запись.
- Отдельный диагностический разборщик с фиксированной частью 44 байта прочитал 8 записей. Их имена, смещения локальных заголовков, CRC32 и размеры совпали с 8 локальными записями файлов.

Согласно спецификации ZIP от PKWARE, фиксированная часть заголовка файла центрального каталога имеет размер 46 байт до переменных полей имени файла, дополнительных данных и комментария. См. [спецификацию ZIP PKWARE APPNOTE](https://support.pkware.com/pkzip/appnote).

**Вывод:** в архиве v1.0.6 воспроизводится дефект структуры центрального каталога: записи ведут себя так, как будто были записаны с фиксированной частью 44 байта вместо стандартных 46. Извлекаемые по локальным заголовкам данные файлов проходят CRC32, но представление центрального каталога не соответствует стандартной схеме. Это может объяснять проблемы совместимости и распаковки. Само по себе это не свидетельствует о вредоносном содержимом.

Проверка установила дефект структуры, но пока не установила, какой этап упаковки или инструмент его создал.

## 5. Сопоставление v1.0.6 с исходниками

Семь файлов реализации/конфигурации, извлечённых из ZIP v1.0.6, были сравнены с соответствующими файлами проверенного исходного дерева v1.0.6:

- `VoiceMeeter-IdleWatcher.ps1` совпал побайтно.
- `VoiceMeeter-IdleWatcher.psd1`, `VoiceMeeter-IdleWatcher.vbs`, три модуля `.psm1` и `VMRIdleWatcherNative.cs` совпали после нормализации переводов строк LF в CRLF.
- `QUICK_START.txt` в это сопоставление исходных файлов не включался.

Это подтверждает текстовое соответствие семи сравнивавшихся файлов реализации/конфигурации. Это не доказывает безвредность всех возможных зависимостей сборки или времени выполнения. Для архива v1.0.5 такое же сопоставление в рамках этого сценария не выполнялось.

## 6. Ограниченный статический анализ исходников

Текстовые файлы из обоих архивов проверялись по выбранным признакам следующих категорий:

- прямые механизмы сетевой загрузки;
- команды изменения настроек Microsoft Defender или добавления исключений;
- распространённые механизмы закрепления через реестр, службы, планировщик заданий, Winlogon или IFEO;
- отдельные механизмы закодированного/динамического исполнения и внедрения в удалённые процессы;
- отдельные признаки доступа к учётным данным, профилям браузеров, cookies и буферу обмена.

Настроенные поисковые правила не сообщили совпадений. Проверки синтаксического разбора PowerShell для исследованных файлов `.ps1` и `.psm1` ошибок разбора не обнаружили.

Это ограниченная проверка по правилам. Она не является исчерпывающим ручным аудитом кода, декомпиляцией, анализом YARA/Sigma или доказательством отсутствия вредоносного поведения. Поиск строк может не обнаружить поведение, реализованное через другие API или косвенные вызовы.

## 7. Результат Microsoft Defender и его ограничения

На GitHub runner с Windows Server 2025:

- служба Defender: включена;
- антивирусная защита: включена;
- защита в реальном времени: **выключена**;
- монитор поведения: **выключен**;
- IOAV/проверка загружаемых файлов: **выключена**;
- команда выборочного сканирования завершилась без сообщения об ошибке выполнения;
- `Get-MpThreatDetection` не вернул обнаружений в истории сканирования этой машины.

Версия сигнатур Defender на момент проверки: `1.463.480.0`.

**Интерпретация:** зафиксирован результат «обнаружений нет» при выборочном сканировании на этом hosted runner. Поскольку защита в реальном времени, монитор поведения и IOAV были выключены, это не эквивалентно проверке на обычной полностью защищённой системе Windows 11. Тест также не воспроизводит репутационную проверку загрузки браузером, Microsoft SmartScreen или решения Google Safe Browsing.

## 8. Выводы

1. Точные исторические ZIP-файлы восстановлены и идентифицированы по SHA-256.
2. Все исследованные локальные записи обоих архивов прошли проверку записанных CRC32.
3. v1.0.5 прошёл проверенные тесты согласованности стандартного центрального каталога.
4. v1.0.6 имеет нестандартную/некорректную структуру центрального каталога: записи соответствуют локальным данным при интерпретации с фиксированной частью 44 байта, но не стандартной частью 46 байт.
5. Семь сравнивавшихся файлов реализации/конфигурации v1.0.6 текстуально соответствуют исходникам v1.0.6 (один побайтно, шесть после нормализации переводов строк).
6. Настроенный статический поиск не сообщил совпадений, но его охват ограничен.
7. Сканирование Defender на hosted runner не сообщило обнаружений, но из-за выключенных компонентов защиты этот результат не даёт окончательного ответа для полностью защищённой пользовательской системы.

**Вердикт о наличии или отсутствии malware не выносится.** Дефект упаковки v1.0.6 подтверждён проверкой структуры архива; причина сообщений Defender и Google остаётся неизвестной. Корректная структура ZIP v1.0.5 сама по себе не доказывает безвредность его содержимого.

## 9. Что ещё необходимо сделать

До того как любой из исторических архивов можно будет считать допущенным к распространению, остаются следующие проверки:

1. повторить скачивание и сканирование на чистой виртуальной машине Windows 11 с актуальными сигнатурами Defender и включёнными защитой в реальном времени, монитором поведения и IOAV;
2. отдельно проверить реакцию браузера/SmartScreen, не смешивая её с файловым сканированием Defender;
3. установить, какая команда или программа упаковки создала дефект центрального каталога v1.0.6, затем пересобрать архив и проверить его независимыми ZIP-разборщиками;
4. выполнить контролируемое наблюдение за работой программы в изолированной виртуальной машине с записью действий с процессами, файлами, реестром и сетью;
5. если детекция конкретного поставщика сохранится, запросить у него точное объяснение классификации или анализ образца.

До завершения этих шагов временная приостановка публичной раздачи Portable ZIP остаётся обоснованной.

## 11. Дополнение от 27 ноября 2026 года: проверка в Windows 11 и ручной статический разбор

Это дополнение расширяет первоначальный отчёт от 26 ноября. Оно уточняет прежние статусы по сканированию в чистой VM и сравнению файлов. Оно не отменяет исходное обнаружение Defender на основном ПК и не выносит вердикт о наличии или отсутствии вредоносного ПО.

### 11.1. Чистая гостевая Windows 11: идентификация и состояние защиты

Испытания проводились сопровождающим проекта в Hyper-V VM VM-Test-Windows11, гостевая система VM-LAB-WIN11:

- Windows 11 Pro 26H2, сборка 10.0.26300.9974.
- Microsoft Defender: AMServiceEnabled, AntivirusEnabled, RealTimeProtectionEnabled, BehaviorMonitorEnabled и IoavProtectionEnabled имели значение True.
- Версия Security Intelligence: 1.463.492.0; время обновления, показанное системой: 27.11.2026 07:20:29.
- ScanOnlyIfIdleEnabled имел значение True. Это настройка планирования фонового сканирования; она не мешала явным проверкам по запросу.
- VoiceMeeter в гостевой системе не устанавливался.

Оба архива были загружены из исторического Git-объекта по адресу raw.githubusercontent.com с привязкой к commit 3befd13. Пользователь сверил размер и SHA-256 загруженных файлов с идентификаторами из раздела 2: значения совпали. При загрузке через Edge пользователь не наблюдал предупреждения браузера. Это наблюдение не является отдельным тестом SmartScreen или репутации запуска.

Для каждого ZIP и соответствующей извлечённой папки была выполнена явная выборочная проверка Microsoft Defender через MpCmdRun.exe с параметрами -Scan -ScanType 3 и -DisableRemediation. Все выполненные явные проверки завершились с ExitCode=0 и сообщением об отсутствии обнаруженных угроз. Для v1.0.6 дополнительно выполнялась проверка через Start-MpScan; она не сообщила об обнаружении. В истории Get-MpThreatDetection по проверенным путям совпадений не было.

Интерпретация: на этой конкретной гостевой Windows 11 при указанных настройках и версии сигнатур Defender не обнаружил угроз в двух архивах и проверенных извлечённых папках. Это важный отрицательный результат, но он не доказывает безопасность файлов, не отменяет детекцию Trojan:Script/Wacatac.H!ml на основном ПК и не объясняет предупреждение Google Search Console.

### 11.2. Повторная проверка архивов и файлов

**v1.0.5:** архив стандартно прочитан средствами .NET ZipFile и tar.exe, затем успешно распакован штатным Expand-Archive. В нём обнаружены восемь файлов и запись каталога верхнего уровня. Все локальные записи прошли CRC32. Семь файлов реализации/конфигурации из архива, включая PS1, PSD1, VBS, три PSM1-модуля и C#-файл, совпали побайтно с соответствующими файлами тега v1.0.5.

**v1.0.6:** .NET ZipFile::OpenRead открыл контейнер, но показал ноль записей; tar.exe сообщил Invalid central directory signature. После независимого ручного разбора восьми локальных записей все CRC32 совпали. Затем восемь файлов были извлечены по локальным заголовкам отдельным статическим скриптом, без запуска содержимого. Семь файлов реализации/конфигурации из архива совпали побайтно с файлами тега v1.0.6. Это подтверждает соответствие извлечённых байтов исходному тегу, но не исправляет дефект центрального каталога ZIP.

Для QUICK_START.txt v1.0.6 чтение PowerShell 5.1 с кодировкой по умолчанию показывало некорректные символы в русском разделе. Повторное чтение с явным -Encoding UTF8 отобразило английский и русский тексты корректно. Это была проблема декодирования при просмотре, а не доказательство повреждения содержимого файла. QUICK_START.txt не входит в сравнение семи runtime/source-файлов.

Итог сравнения семи файлов между тегами v1.0.5 и v1.0.6: побайтно одинаковы VBS, Support.psm1, Interop.psm1, MacroButtons.psm1 и VMRIdleWatcherNative.cs. Изменились только основной PS1 и PSD1. В PSD1 значения настроек сохранены; изменения относятся к поясняющим комментариям и форматированию. В PS1 изменены версия, очистка временного флага после подтверждённой остановки движка/успешного повторного Login и представление состояния MacroButtons в журнале. Интервал снимка статуса увеличен с 60 до 300 секунд. Новых сетевых или системных механизмов в этом diff не обнаружено.

### 11.3. Ограниченная проверка реального стартового отказа v1.0.6

Пользователь подтвердил, что VoiceMeeter в VM не установлен. Прямая проверка реестра и стандартных каталогов не нашла VoicemeeterRemote64.dll. После этого пользователь запустил двойным щелчком только VoiceMeeter-IdleWatcher.vbs при отключённом сетевом подключении гостя. Появилось окно ошибки; в журнале была запись о том, что VoicemeeterRemote64.dll не найден.

Это подтверждает конкретную fail-fast ветку: VBS запустил отдельный Windows PowerShell, основной скрипт дошёл до поиска Remote API DLL и завершил старт с ошибкой. По проверенному порядку операций поиск DLL выполняется до компиляции C#-обвязки, создания display/stop interop и входа в VoiceMeeter API. Поэтому в этом запуске не выполнялись API Login, основной цикл и вызов VoiceMeeter-параметра Command.Shutdown. Это не полноценный runtime-тест рабочего режима: VoiceMeeter и его DLL в VM отсутствовали.

При прямой попытке Import-Module из интерактивной консоли PowerShell 5.1 система заблокировала импорт действующей политикой выполнения. VBS запускает PowerShell с -ExecutionPolicy Bypass, поэтому запуск через лаунчер прошёл дальше. Этот параметр относится к запущенному процессу/сеансу PowerShell; он не изменяет постоянно системную политику и не отключает Microsoft Defender. Microsoft отдельно указывает, что Execution Policy не является границей безопасности, а Group Policy имеет более высокий приоритет: [документация Microsoft для Windows PowerShell 5.1](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_execution_policies?view=powershell-5.1).

### 11.4. Результат ручного статического просмотра семи исходных файлов

Просмотрены PS1, PSD1, VBS, три PSM1-модуля и VMRIdleWatcherNative.cs тега v1.0.6, а также разница с v1.0.5.

Назначение и наблюдаемые действия:

- VBS проверяет наличие соседнего PS1 и Windows PowerShell, затем запускает PowerShell скрыто, без профиля и интерактивного ввода. Для старта использует временный status-файл в TEMP, ожидает READY/FAILED и показывает окно при ошибке. Команда /stop передаёт запрос штатной остановки и ожидает подтверждения; принудительно процесс не убивает.
- PS1 загружает и валидирует PSD1, подключает три соседних модуля, создаёт локальную защиту от второго экземпляра через именованный mutex и ведёт журнал. Значения конфигурации ограничены проверяемыми диапазонами.
- Interop.psm1 читает из HKLM данные раздела деинсталляции VoiceMeeter (InstallLocation и UninstallString) и проверяет типовые каталоги Program Files. Записи реестра не создаются и не изменяются. После нахождения библиотеки исходник C# читается из папки программы, в него подставляется путь DLL и он компилируется через Add-Type.
- C# получает только время последнего пользовательского ввода через GetLastInputInfo, состояние дисплея через уведомления Windows Power API и сигналы именованных событий. Объявлены вызовы Remote API VoiceMeeter: Login, Logout, IsParametersDirty, SetParameterFloat и MacroButton_SetStatus.
- MacroButtons использует один централизованный путь записи с фиксированным STATEONLY 0x00000002. Чтение состояния кнопки обратно не выполняется. Код 0 фиксирует принятие команды API, а не подтверждение того, как состояние отобразилось в интерфейсе.
- Command.Shutdown вызывается как параметр VoiceMeeter Remote API через SetParameterFloat. Это запрос выключения движка VoiceMeeter, а не команда завершения работы Windows.
- Файловая запись ограничена журналами и временным startup-status handshake. При ротации удаляется прежний .old-файл собственного журнала; временный status-файл удаляется после чтения лаунчером. Постоянных записей автозапуска в реестр, служб или задач планировщика в просмотренном коде нет.

В просмотренных исходниках не обнаружены прямые сетевые клиенты/загрузки, изменение настроек Defender или добавление исключений, сбор учётных данных, чтение браузерных хранилищ/cookies/буфера обмена, внедрение в чужие процессы, создание служб/задач планировщика или механизмы закрепления через Run/Winlogon/IFEO. Это результат ручного анализа именно этих файлов, а не доказательство отсутствия любых возможных вредоносных свойств всех внешних зависимостей и окружения.

Два аспекта следует явно учитывать:

1. VBS сочетает скрытый запуск PowerShell с -NoProfile, -NonInteractive и -ExecutionPolicy Bypass. Это функционально объясняется портативным лаунчером и отсутствием консольного окна, но такая комбинация может выглядеть подозрительно для эвристических классификаторов. Нельзя утверждать, что именно она вызвала Wacatac: для этого нет данных.
2. Путь к Remote API DLL выбирается по значениям реестра/типовым каталогам, но сам проект не проверяет цифровую подпись издателя и не закрепляет ожидаемый хэш DLL. Это граница доверия к установленной зависимости VoiceMeeter, а не обнаруженный факт подмены библиотеки.

### 11.5. Упаковка ZIP и оставшиеся неизвестные

В текущей ветке main найден только workflow powershell-check.yml, который разбирает PowerShell 5.1, проверяет контракты проекта, компилирует встроенный C# и проверяет ошибочный аргумент VBS. Он не создаёт Portable ZIP. Поиск Compress-Archive и аналогичной команды в доступном исходном дереве main не обнаружил сборочного рецепта. Исторические коммиты добавления/замены ZIP в gh-pages затрагивали только бинарный архив. Поэтому инструмент и точный этап, создавшие 44-байтовую структуру центрального каталога v1.0.6, остаются неизвестными.
